# Space Client — техническое задание сайта v1.0

Дата: 23 октября 2026. Стадия: ТЗ перед проектированием нового интерфейса. Приоритет пользователя — сайт; игровой клиент остаётся отдельным направлением. Технологии утверждены: Next.js + NestJS, TypeScript. Документ задаёт следующий результат, а не описывает всё как уже реализованное.

## 1. Цель

Сайт должен за одну короткую сессию объяснить, что такое Space Client, какие возможности доступны сейчас, как получить клиент после релиза и где найти помощь. До выпуска клиента сайт работает как полноценная страница проекта с прозрачным статусом разработки.

Основные действия: понять продукт → изучить возможности → открыть загрузки → скачать существующую совместимую сборку или увидеть причину её отсутствия. Дополнительные: прочитать обновления, инструкцию и отправить bug report через GitHub.

Успех первой версии проверяется прохождением сценариев и техническими измерениями. Число пользователей, отзывов, скачиваний и прирост FPS не выдумываются.

## 2. Аудитория и рабочие допущения

- Новичок: не знает разницы между лаунчером, модом и Minecraft. Нужны понятное объяснение и последовательность установки.
- PvP-игрок: ищет Minecraft 1.8.9, HUD, CPS, Keystrokes и информацию о совместимости.
- Текущий пользователь: хочет обновление, changelog, требования или решение проблемы.
- Наблюдающий за разработкой: хочет реальный прогресс и исходники.

Рабочие решения первой версии: русский язык, Windows x64 как первая целевая платформа клиента, тёмная тема. Пользователь не выбирал конкретный шрифт, палитру или хостинг — они определяются на этапе визуального проекта и фиксируются отдельно. Вебсайт должен открываться также на телефонах и других ОС.

## 3. Объём первой версии

Входят: многостраничный публичный сайт, каталог возможностей, загрузки с корректным пустым состоянием, новости разработки/changelog, помощь, NestJS read-only API, responsive UI, SEO, проверки и инструкции размещения.

За пределами первой версии: регистрация на сайте, личный кабинет, Microsoft-вход в браузере сайта, магазин, платежи, косметика, друзья, cloud sync, чат, рассылка, админка и пользовательская загрузка файлов. Игровая авторизация относится к лаунчеру и не требуется для чтения сайта.

Сайт не блокируется отсутствием игрового релиза. Публикация настоящего установщика зависит от игрового направления; готовность дизайна и пустого каталога от него не зависит.

## 5. Общая оболочка и навигация

Header: самостоятельный знак Space Client, ссылка на главную, Возможности, Скачать, Обновления, Помощь; GitHub — вторичное действие. Текущая страница выделяется визуально и через `aria-current`. Логотип всегда ведёт на `/`.

На узком экране навигация становится компактным раскрывающимся меню с понятной кнопкой. При overlay: Esc закрывает, focus удерживается внутри открытого меню и возвращается к кнопке; фон не прокручивается. После перехода меню закрывается. Меню доступно без hover.

Footer: название, краткий статус, навигация, репозиторий, реальные контакты поддержки/issue tracker и сведения о самостоятельном проекте. Не добавлять несуществующие Discord/социальные ссылки.

Общие элементы: skip-link, ограничение ширины текстовых блоков, breadcrumbs на вложенных страницах, однозначные подписи кнопок и состояние загрузки без скачков layout. GitHub, технический health API и внутренние номера задач не занимают место основных продуктовых действий.

## 6. Главная `/`

Порядок блоков:

1. Hero: Space Client, одно ясное объяснение продукта, текущая стадия. Визуальный образ создаёт космический характер, текст остаётся главным.
2. Основное действие «Перейти к загрузкам», вторичное «Возможности». До релиза рядом явно «Пользовательская сборка ещё не выпущена». Не использовать кнопку «Скачать сейчас», если скачивать нечего.
3. Краткая совместимость: целевая версия Minecraft и платформа с пометкой «планируется», пока нет пользовательской сборки.
4. Три–четыре предметных направления: HUD, модули, профили, удобство запуска. Каждое со статусом и ссылкой на подробности.
5. Демонстрация HUD/интерфейса: настоящий снимок или явно подписанный концепт. Нельзя изображать макет как готовый игровой экран.
6. «Как начать»: знакомство → проверка совместимости → загрузка → установка. До релиза блок объясняет предстоящий путь и ведёт к статусу разработки.
7. Последняя опубликованная новость. Если новостей нет — компактный блок о текущем этапе без фиктивной даты релиза.
8. Несколько FAQ и ссылка на помощь.

На первом экране видно название, назначение, текущий статус и основное действие на desktop и mobile. Никакого обязательного просмотра анимации перед навигацией.

## 7. Возможности `/features`

Категории: HUD, управление/удобство, профили/лаунчер, производительность. Поиск по названию/краткому описанию и фильтры по категории и состоянию. Значения фильтров отражаются в query-параметрах и восстанавливаются после Back/перезагрузки. Не добавлять категорию без контента.

Карточка содержит название, краткое описание, категорию и текстовый статус. Использовать состояния:

- `planned`: запланировано;
- `prototype`: реализовано в dev-прототипе, проверка пользователем ещё не завершена;
- `verified`: проверено в dev-сценарии, но может ещё не быть в публичном релизе;
- `released`: доступно в указанной пользовательской версии.

Для `released` обязательна связь с настоящим релизом. «Реализовано» не означает «скачать уже можно». Статусы не передаются одним цветом.

Начальное содержимое отражает факт: FPS/координаты/состояния клавиш/F8 — прототип; CPS, редактор HUD, полноценные launch-профили — план. Оптимизацию не выдавать за готовую функцию без результата измерения.

Подробности карточки — раскрываемая область в самой странице с описанием, ограничениями и связанными ссылками. Отдельные SEO-страницы для каждого модуля пока не требуются. При пустом поиске: текст «Ничего не найдено», активные фильтры и «Сбросить фильтры»; введённый запрос сохраняется.

## 8. Загрузки `/download`

### До первого релиза

HTTP 200, понятный текст об отсутствии пользовательской сборки, целевые Minecraft/ОС, ссылка на обновления и помощь. Программирование версии сайта не считается релизом клиента. Dev jar не показывается как Windows-установщик. Кнопки скачивания нет; нет искусственного таймера ожидания.

### При наличии релиза

Карточка: название клиента, версия, канал (`alpha`, `beta`, `stable`), дата, платформа, архитектура, поддерживаемые версии Minecraft, размер, SHA-256, статус подписи, ссылка на changelog и инструкцию. Кнопка содержит платформу и формат файла.

Начальный поддерживаемый артефакт — Windows x64. Другие платформы показываются только как недоступные с пояснением; не создавать бутафорские активные вкладки. Определение ОС может предложить вариант, но не скрывать остальные данные и не скачивать автоматически.

Выбор по умолчанию: самый новый совместимый `stable`, иначе самый новый совместимый prerelease с заметной меткой. Сортировка по publication timestamp, при равенстве — стабильный ID. Канал выбирается явно при наличии нескольких каналов; pre-release не маскируется под stable.

Клик ведёт прямо на разрешённый HTTPS-артефакт, без промежуточной рекламы и произвольного redirect API. Во время начала запроса нельзя обещать успешное сохранение файла: браузер сам управляет скачиванием. SHA-256 копируется отдельной кнопкой со статусом «Скопировано»/ошибкой и возможностью выделить текст вручную.

Требования к RAM, диску и Java публиковать только после измерений/выбора runtime. До этого — «будут уточнены перед alpha», без выдуманных минимальных значений. Если артефакт отозван или URL не прошёл проверку, убрать действие скачивания и показать пояснение.

## 9. Обновления `/updates`

Лента содержит реальные заметки разработки и релизы с разными метками, заголовком, summary и датой. Даты API — ISO UTC, посетителю — локализованная дата с машинным `datetime`. Не присваивать заметке статус релиза, если установщика нет.

Карточка ведёт на `/updates/[slug]`. Статья: заголовок, тип, дата, вводный абзац, разделы «Добавлено», «Исправлено», «Известные ограничения» по необходимости. Связь с релизом отображается только при наличии releaseId. Неизвестный или неопубликованный slug — 404.

Первая версия: до 12 записей на страницу; пагинация в query, стабильный порядок по publishedAt/id, фильтр `all/development/release`. При пустой ленте — сообщение без искусственных карточек. Пагинация работает прямой ссылкой и через Back.

## 10. Помощь `/help`

Каталог тем: состояние разработки, совместимость, начало работы, HUD, диагностика, сообщения об ошибках. До релиза инструкция установки описывает только доступный способ и явно указывает статус; нельзя предлагать несуществующие кнопки лаунчера.

Поиск первой версии — локальный по заголовкам/summary FAQ и инструкций, без внешнего поискового сервиса. Результаты содержат заголовок, тип и ссылку. Пустой результат предлагает сбросить запрос и открыть issue.

Статья: название, дата актуализации, применимая версия, пошаговые действия и результат. Для ожидаемой ошибки — причина, что проверить и какие сведения приложить к bug report. Просить очищенные логи; не просить пароль, access/refresh token или личные документы.

FAQ раскрывается с клавиатуры; несколько пунктов могут быть открыты одновременно. Ссылка на GitHub bug form не требует собственного backend формы или приёма вложений на нашем сайте.

## 12. Состояния и ошибки

| Состояние | Отображение и поведение |
|---|---|
| Данные ещё загружаются | Skeleton нужного размера, не бесконечный spinner; сохраняется layout |
| Валидный пустой ответ | Предметное сообщение «Релизов пока нет»/«Записей пока нет» |
| Timeout/API 5xx | «Не удалось загрузить…», кнопка повторить и переход к помощи; не текст «релизов нет» |
| Некорректный JSON/схема | Безопасное состояние ошибки, никакого скачивания по невалидным данным |
| Неизвестный slug | Настоящий HTTP 404, ссылки на раздел/главную |
| Ошибка копирования | Видимый хеш остаётся доступным для ручного выделения |
| Общая ошибка страницы | Понятное сообщение, retry/назад; без stack trace и внутренних адресов |

Кнопка повторить делает новый ограниченный запрос. Автоматические бесконечные повторы запрещены. Ошибка одного блока главной не должна уничтожать всю страницу. В production убрать публичную техническую надпись «API подключён»: пользователю важны данные и их состояние.

## 13. Визуальное задание перед разработкой UI

Характер: космический, спокойный, современный gaming-продукт. Самостоятельное оформление Space Client; не копировать интерфейсы и логотипы конкурентов. Тёмный нейтральный фон, светлая типографика, один основной акцент; текущий мятный цвет — кандидат, не окончательное решение.

Перед кодом нового UI подготовить: контентные wireframes всех шаблонов, макет главной desktop/mobile, типографическую шкалу, palette/tokens, навигацию, карточки, badges, buttons, inputs, FAQ и error/empty states. Затем применить одну систему ко всем страницам.

Интерфейс должен быть приятным за счёт иерархии, читаемости, расстояний и понятных действий. Не перегружать каждый блок стеклом, glow, частицами и анимацией. Космическая иллюстрация помогает бренду, но не закрывает текст и не несёт единственную копию важной информации.

Шрифты поддерживают кириллицу, не более двух семейств; системный fallback обязателен. Иконки в едином SVG-стиле. Реальные скриншоты отмечать версией, концепты — подписью. Размеры изображений заданы заранее, тяжёлые изображения ниже первого экрана загружаются отложенно.

Hover/press/focus/error/disabled состояния фиксируются для каждого control. Анимации короткие, без обязательного autoplay-видео и тяжёлого WebGL; при reduced-motion декорация статична. Cookie banner не добавляется без фактической потребности.

## 14. Адаптивность и доступность

- Проверочные ширины: 375, 390, 768, 1024, 1440 px; дополнительно 320 px и 200% zoom для reflow.
- Нет горизонтального scroll страницы; длинный hash/URL переносится или прокручивается внутри отдельного блока.
- Читаемая мера строки, основной текст ориентировочно 16–18 px; ограничения размеров не мешают zoom.
- Все действия доступны клавиатурой, порядок focus соответствует чтению, outline не скрывается. Header не перекрывает focused control и якорь.
- У элементов управления есть labels и доступные имена; placeholder не заменяет label. Статусы не выражены только цветом.
- Целевые контрасты: 4.5:1 обычный текст, 3:1 крупный текст и значимые control boundaries. Проверить выбранные цвета инструментом, не «на глаз».
- Основные touch targets не меньше 44×44 CSS px; не полагаться на hover. У важных сообщений корректный live-region без повторного озвучивания всей страницы.
- Один H1 на страницу, последовательные headings, корректные landmarks и альтернативные подписи значимым изображениям.

Это проверяемые требования проекта, а не декларация сертификации доступности.

## 15. Архитектура frontend

Next.js App Router, TypeScript strict. Server Components для контента и первичной загрузки; Client Components только для меню, поиска/фильтров, copy/retry и другой интерактивности.

Предлагаемая структура: `app/` — routes/layout/loading/error/not-found; `components/layout`, `components/ui`, `components/features`; `lib/api`, `lib/content`, `lib/validation`; `public/` — собственные assets. Не создавать отдельную копию общей навигации на каждой странице.

NestJS вызывается с Next-сервера по `SPACE_API_URL`, не по адресу, зашитому в браузер. Браузерные query-фильтры применяются к уже безопасным DTO; для retry использовать ограниченный same-origin путь/серверное действие, не произвольный URL от клиента. Серверные секреты не попадают в NEXT_PUBLIC-переменные.

Timeout на server-to-server запрос — 2 секунды на попытку. Релизные данные можно кешировать до 60 секунд, контент — до 5 минут; текущую стратегию выбрать и проверить в коде. После исправления критичного релиза предусмотреть принудительную инвалидацию кеша. Не кешировать ошибку как валидный пустой список.

## 16. NestJS API и модели

API префикс `/v1`. Следующий контракт проектируется сейчас; текущий API частичный, его изменение отражается в HTTP-тестах и frontend вместе.

| Endpoint | Успешный ответ | Ошибки/ограничения |
|---|---|---|
| `GET /health` | Готовность процесса | Не выдаёт env/секреты |
| `GET /project` | Стадия, имя, цели совместимости | Фиксированный валидируемый DTO |
| `GET /features` | `{items: Feature[]}` | Данные со статусами, без выдуманных релизов |
| `GET /releases` | `{items: Release[], total}` | Пустой items — реальное отсутствие релизов |
| `GET /updates?type=&page=` | `{items, page, pageSize, total}` | type enum, page integer >=1, pageSize=12 |
| `GET /updates/:slug` | Одна публичная запись | Невалидный ввод 400; неизвестная запись 404 |

Инструкции и FAQ в первой версии — versioned frontend content; дополнительный API для них не нужен. Ошибки API: стабильный `{statusCode, code, message}` с безопасным сообщением; без stack trace. Ошибочный query не игнорируется молча.

`Feature`: id/slug, name, summary, category, status, details, optional releaseId и preview с подписью. Enum проверяется на сервере; связь released→releaseId валидируется.

`Release`: id, version, channel, publishedAt ISO UTC, minecraftVersions[], changelogSlug, artifacts[]. Каждый artifact: platform, architecture, fileName, sizeBytes positive integer, sha256 (64 hex), HTTPS downloadUrl из allowlist, signatureStatus (`signed/unsigned/unknown`). Непроверенные артефакты не допускаются к публикации. Конкретный release не обязан поддерживать несколько платформ.

`Update`: id/slug, type (`development/release`), title, summary, publishedAt, typed content blocks, optional releaseId. Slug уникальный; даты валидны; релизная статья ссылается на реальную запись каталога.

Скачивания размещаются как assets GitHub Releases. Allowlist настраивается сервером для конкретного репозитория; не принимать URL из query как redirect. Внешние assets и другой storage — отдельное изменение контракта.

## 17. Управление контентом

Первая версия без админки и БД: данные API — типизированные versioned файлы внутри `apps/api`; help — frontend content. Содержимое проходит проверку схемы и CI, затем commit/review/deploy. Для статьи используются безопасные типизированные блоки или статический доверенный MDX; пользовательский HTML не исполняется.

Публикация релиза: проверенный артефакт → запись release → соответствующая release-статья → CI → размещение → проверка ссылки и хеша. Источники release/changelog согласуются; номер версии сайта не становится автоматически номером игрового клиента.

Контент главной и Feature status обновлять по фактическому прогрессу. Планируемое не переводится в released из-за одного commit. При отзыве артефакта сначала выключить скачивание и кеш, затем публиковать объяснение.

## 18. SEO и измеримые технические цели

Уникальные title/description, canonical с настроенным origin, корректные Open Graph metadata. Preview/local не индексируются. Sitemap включает только публичные существующие страницы и статьи; robots соответствует окружению. Не публиковать placeholder-домен в canonical.

Ключевые тексты доступны в server-rendered HTML без ожидания browser API. Loading/error/404 страницы не индексируются как полезные статьи. Metadata неизвестного slug не превращает его в HTTP 200.

Цели приёмки на согласованном mobile-профиле, production build, медиана трёх Lighthouse-прогонов: Performance >=90, Accessibility >=95, SEO >=95; CLS <=0.1, LCP <=2.5 s на выбранном стенде. Это лабораторные цели, не гарантия для любого устройства/сети. Сохранить версию инструмента и условия теста. Ошибки console, hydration и неуспешные собственные assets отсутствуют.

Сторонняя аналитика, tracking cookies и формы сбора email по умолчанию не подключаются. Если появится потребность — отдельно определить события, объём данных и тексты о приватности. Не устанавливать маркетинговые KPI без настоящих данных.

## 19. Безопасность и размещение

Read-only API первой версии не требует пользовательской авторизации. Нельзя добавлять незащищённые POST endpoints для публикации контента. Нет загрузок файлов на наш сервер и исполнения внешнего HTML. Размеры query/параметров ограничены, выходные DTO валидны.

Production: HTTPS, корректные content/security headers, CSP совместимая с Next.js, запрет embedding, отсутствие stack trace. CSP проверяется на реальных Next assets; не блокировать собственную hydration и не включать произвольные внешние скрипты ради обхода ошибки.

Хостинг должен поддерживать Next.js и NestJS как два Node-сервиса. Внутренний адрес API и bind настраиваются окружением, API по возможности закрыт за внутренней сетью/reverse proxy. Таймауты/лимиты задаются также на proxy. Домен, провайдер, бюджет и тексты юридических страниц — решения перед production, не блокируют local UI.

Deployment runbook: install из lockfile → tests → production build → запуск с env → health check → проверка routes → переключение версии; при ошибке — возврат к предыдущему commit/artifact. Не хранить ключи и runtime-файлы в репозитории. Логи без токенов и содержимого приватных отчётов.

## 22. Что делаем следующим

ТЗ фиксируется отдельным commit. Затем проектируем визуальную систему и wireframes, после этого реализуем интерфейс по W2–W6. Готовность отдельных этапов отмечается в GitHub Issues. Аккаунты/магазин/новый backend стек не добавляются без отдельной задачи.

Первое ТЗ не является просьбой подтвердить каждую мелочь: разумные детали реализуются в этих границах. Изменения объёма, платные услуги и внешние зависимости сначала фиксируются конкретным предложением. Все неопределённости выше явно отделены от утверждённого стека и проверяемых требований.
