## Организация прохода

Пользователь запускает Narrator и открывает согласованный локальный QA-адрес сам, когда удобно. Агент не открывает окна, не меняет системные настройки и не использует Computer Use. Перед проходом записать версию Windows/Narrator, браузер и его версию, URL, commit сборки, масштаб и размер окна. Не использовать исторический localhost URL без проверки доступности. Действующие пользовательские браузерные профили не менять.

Начать с N1–N3 в обычном окне. Tab/Shift+Tab перемещают фокус, Enter активирует ссылку/кнопку; чтение headings/landmarks выполнять привычными командами Narrator. Если команда неизвестна, сначала использовать встроенную справку Narrator. Ожидается смысл сообщения, а не побуквенное совпадение: формулировки зависят от версии и настроек AT. Отсутствие озвучивания записывать явно. DOM или автоматическая проверка не заменяют услышанное.

N8–N9 сейчас заблокированы до подготовки отдельного управляемого QA-стенда и согласования времени ручного прохода. Не останавливать общий API ради имитации ошибки и не добавлять фиктивные релизы в production. Если задержка недостаточна для восприятия pending, этот подпункт не считать проверенным. N6 требует пользовательского изменения размера окна; headless mobile emulation не является ручным Narrator-проходом.

Шаблон результата для каждого ID: `дата / URL / commit / Windows и Narrator / браузер / размер и zoom / действия / фактически услышано / положение фокуса / PASS или FAIL или BLOCKED / замечания`. Общего «всё работает» недостаточно для всех пунктов. До результатов N1–N9 ручная AT-приёмка остаётся открытой.

## Передача production HTTPS/SEO после SC-24

Cloudflare выбран в отдельном чате SC-24 по сообщению пользователя; проверенного публичного URL и deployment evidence в текущем срезе нет. Сайт этим протоколом не публикуется. SC-23 требует публичного окружения от SC-24, а SC-24 ссылается на SC-23: локальный срез уже позволяет готовить размещение, но обе задачи сохраняют незакрытые production-критерии.

После появления окружения собрать свидетельства:

1. SC-24 передаёт точный HTTPS-origin, commit/build, конфигурацию индексации на момент build, health и rollback evidence. Проверить HTTP → HTTPS, валидность TLS и финальный origin без циклических redirect. Не изменять Cloudflare из этого чата.
2. На реальных ответах проверить пять основных маршрутов, прямые URL статей/инструкций и настоящий HTTP 404 неизвестных slug; content/security headers, отсутствие публичного stack trace и доступность собственных ресурсов. Убедиться, что CSP не ломает hydration, нет mixed content, console/page errors и failed assets. Выполнить browser smoke без загрузки артефактов.
3. Пока preview не принят, сохранить noindex, запрет robots и пустой sitemap. После разрешённого в SC-24 включения индексации и новой сборки проверить уникальные title/description, canonical и Open Graph с final HTTPS-origin, доступную OG-картинку и sitemap только с существующими публичными страницами. Проверить отсутствие неожиданного X-Robots-Tag от proxy. Не подменять noindex ради оценки Lighthouse.
4. Только на готовом публичном origin выполнить отдельную production-серию по разделу 18 WEBSITE-SPEC: согласованный mobile-профиль, медиана трёх прогонов каждого из пяти основных маршрутов; Performance ≥90, Accessibility ≥95, SEO ≥95, CLS ≤0.1, LCP ≤2.5 s. Записать версии, профиль, даты, commit и все наблюдения. Прежняя локальная серия из WEB-PERFORMANCE остаётся локальной и повторно здесь не запускалась.
5. Обновить WEB-01–WEB-12 фактическими результатами, сохранив отдельные пробелы Narrator/Safari. Не закрывать #23 до выполнения всех критериев.

Metadata сверена через Codebase Memory (graph → snippet → coverage) и с диском: `metadata.ts`, `robots.ts`, `sitemap.ts`. Все три пути имеют `metadata_changed`; документация исключена из индекса. Полнота/свежесть индекса не доказана. Исходники подтверждают условия включения индексации, но не наличие production HTTPS или корректность размещения.
