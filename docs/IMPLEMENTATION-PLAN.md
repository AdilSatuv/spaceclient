# Space Client: подробный план разработки

Дата начала: 23 октября 2026. План ведёт к работающей alpha Minecraft Java 1.8.9 для Windows x64, вместе с сайтом. Полный аналог многолетних клиентов — отдельная долгосрочная цель, а не обещание первого релиза.

Обновление приоритета: пользователь уточнил, что следует начать с самого лаунчера. SC-07/09 завершены; 24 октября после завершённой SC-02 пользователь выбрал локальный ник и запуск SC-25. Этот сценарий реализован отдельно от официального SC-06/08/10: см. LOCAL-LAUNCH.md. Собственная Space-регистрация — отдельный будущий срез, Microsoft отложен. Локальный каркас настроек независим от завершения SC-02; эту зависимость сняли в tasks.json. Незавершённые задачи HUD и сайта сохраняются в трекере.

## Состояние раннего этапа

Актуальное состояние на 24 октября — CHAT-HANDOFF.md и LOCAL-LAUNCH.md; список ниже сохранён как исходная точка плана.

- Исследование официальных материалов и начальное ТЗ.
- Локальные JDK 21, Gradle wrapper, Git, Node.js и npm; GitHub CLI установлен отдельно в `.tools`.
- Java-мод Legacy Fabric: FPS, CPS, XYZ, состояния движения, событийный F8 и файл конфигурации. Компиляция и 9 unit-тестов подтверждены; проверки в мире и незакрытые сценарии записаны в SMOKE-TEST.md.
- Next.js App Router + NestJS: главная страница, API статуса и пустого списка релизов, server-to-server запрос с fallback.
- Проверки в CI; предыдущая сборка workflow Verify завершилась успешно.
- Создан исходный desktop-каркас лаунчера с локальными профилями и диагностикой Java; визуальная приёмка ещё не пройдена. Нет Microsoft-входа, установки Minecraft, HUD editor, установщика и публичного релиза.

## Как устроен продукт

| Часть | Технология | Ответственность |
|---|---|---|
| Игровой мод | Java, Legacy Fabric, Mixin | HUD, клавиши, настройки и отрисовка в Minecraft |
| Лаунчер | Планируется Electron + TypeScript | Учётная запись, профили, runtime, файлы, запуск и логи |
| Сайт | Next.js + TypeScript | Описание, помощь, новости и загрузки |
| API | NestJS + TypeScript | Статус проекта и проверенный каталог релизов |
| Хранение | Локальные versioned configs; позже БД по задаче | Настройки игрока отделены от сайта |
| Доставка | GitHub Actions, tags, release artifacts | Повторяемая сборка и проверяемая версия |

Критическая цепочка: стабильный dev-клиент → рабочие модули → авторизованный запуск → испытания → alpha. Проверку доступности игровых Microsoft API нужно вести заранее: она может потребовать действий владельца аккаунта и стать внешней зависимостью.

## M1. Игровой фундамент — SC-01–03

1. Проверить зависимости и wrapper; закрепить версии, контрольные суммы и Java bytecode target.
2. Исправить несовместимость Log4j: одинаковая версия API/Core, клиентский конфиг без server GUI appender, рабочий latest.log. Не скрывать настоящие ошибки игры фильтрами.
3. Запустить dev-клиент; проверить загрузку Mixin и отсутствие аварии инициализации.
4. Создать тестовый singleplayer-мир. Сравнить XYZ с F3, FPS — с игровым показателем, клавиши — с текущими bindings.
5. Проверить F8: короткое нажатие, удержание, меню паузы, возврат, перезапуск. Проверить F1/F3, смену разрешения и GUI scale.
6. Добавить CPS через реальные события мыши. Использовать монотонные часы и скользящее окно; считать LMB/RMB отдельно. Не считать удержание повторными кликами и исключить клики меню.
7. Записать результаты в smoke-test отчёт: дата, версии, шаги, ожидаемое/фактическое поведение, ошибки.

Выход: проверяемый в мире HUD, а не только успешно скомпилированный jar.

## M2. Модули и редактор — SC-04–05

8. Ввести реестр модулей: стабильный ID, название, enabled, настройки, событие обновления и отрисовка.
9. Разделить получение данных и UI: счётчики не должны зависеть от конкретного виджета.
10. Создать экран модулей: поиск, переключатели, настройки и горячая клавиша. Esc закрывает экран без потери изменений.
11. Сохранение: версия схемы, значения по умолчанию, миграции, проверка входных значений, безопасная замена файла. Не затирать повреждённые данные без возможности восстановления.
12. Добавить HUD editor: выделение, перемещение, масштаб, привязки к краям, сброс. Координаты не должны выводить виджет за экран при смене разрешения.
13. Добавить два независимых HUD-профиля, переключение, переименование, экспорт и валидируемый импорт.
14. Проверить редактор на 720p/1080p и нескольких GUI scale; проверить конфликт клавиш и resource packs.

Выход: игрок настраивает HUD из игры, без ручного редактирования файла.

## M3. Лаунчер и вход — SC-06–08

15. Проверить регистрацию Microsoft public client, требования Xbox/Minecraft API и права нашего приложения. Не считать обычный OAuth доказательством рабочего игрового входа.
16. Зафиксировать решение о desktop-стеке и границах процессов. Начальный кандидат — Electron/TypeScript; измерить размер и RAM.
17. Создать главное окно и экран профиля: версия, RAM, runtime, каталог, статус. Только main process работает с диском и процессами.
18. Настроить sandbox, context isolation, CSP, запрет произвольной навигации и проверяемый IPC. Проверять отправителя и аргументы каждого privileged вызова.
19. Реализовать системный браузер, PKCE/state и callback. Обработать отмену, timeout и повторное нажатие входа.
20. Выполнить цепочку Microsoft → Xbox → XSTS → Minecraft token → entitlement/profile. Проверить отсутствие лицензии и понятное сообщение пользователю.
21. Хранить refresh token через средства ОС, реализовать обновление и выход. Не передавать токены renderer и не писать в логи/репозиторий.

Выход: вход законным аккаунтом, сохранённый профиль и корректное завершение сессии.

## M4. Установка и реальный запуск — SC-09–10

22. Описать install manifest: версия игры, loader, Java, libraries, assets, natives, хеши и допустимые источники.
23. Сделать установку изолированного инстанса с ограничением путей. Загрузки пишутся во временные файлы; готовый файл принимается после проверки.
24. Добавить прогресс, повторы с ограничением, отмену и восстановление. Повреждение одной библиотеки не должно требовать полной переустановки.
25. Безопасно распаковать natives; запретить выход из каталога инстанса и обход путей через архив.
26. Собрать classpath/JVM/game args, заменить credentials в памяти, запускать Java без shell.
27. Сделать состояния preparing/downloading/ready/running/failed, блокировку двойного запуска, обработку выхода и очищенные логи.
28. Пройти путь на чистом Windows-профиле: сайт → установка лаунчера → вход → скачивание игры → мир → повторный запуск.

Выход: настоящий пользовательский вертикальный сценарий, а не кнопка запуска dev-task Gradle.

## M5. Сайт и API — SC-11–12

29. Доработать Next.js страницы: главная, возможности, помощь, changelog и загрузки. Писать только о фактических возможностях; будущие функции помечать.
30. Проверить 375/768/1440 px, keyboard/focus, FAQ, контраст, метаданные и страницы ошибок.
31. Проверить поведение при недоступном NestJS и медленном ответе; основной текст сайта остаётся доступным.
32. Определить контракт релиза: version/channel/platform/date/checksum/download URL. API не должен отдавать выдуманные сборки.
33. Добавить публикацию каталога через контролируемый релизный процесс. Произвольный пользователь сайта не может записывать URL загрузки.
34. Добавить реальную кнопку скачивания только после готового артефакта и проверки его установки.

БД вводится при появлении необходимости редактировать долговечные данные через сервис. Аккаунты сайта, магазин и платежи в MVP не включены.

## M6. Производительность и совместимость — SC-13

35. Определить тестовый мир, маршрут, настройки, разрешение, прогрев и длительность прогона.
36. Выполнить минимум три прогона vanilla, Space без HUD, Space с HUD на одной машине. Сохранить конфигурацию железа и raw результаты.
37. Сравнить average FPS, 1% low, frametime, память и время запуска. Любую оптимизацию проверять до/после отдельно.
38. Испытать alt-tab, resize, сворачивание, resource packs, F1/F3, повторный вход в мир и длительную сессию.
39. Исправить регрессии, а затем писать проверяемые заявления о производительности. Не переносить маркетинговые цифры конкурентов.

Выход: список известных ограничений и подтверждённые измерения.

## M7. Alpha и размещение — SC-14–15

40. Создать tag/release workflow: мод, Windows-лаунчер, версии и контрольные суммы связаны с одним commit.
41. Проверить установку/удаление и сохранность настроек; описать восстановление и rollback.
42. Определить подпись установщика и канал обновлений. Хеш файла не заменяет проверку подлинности издателя.
43. Выбрать хостинг Next.js/NestJS, domain/TLS, bind-адреса, API URL, health checks и секреты окружения. Расходы и платные услуги согласовать до подключения.
44. Разместить сайт и API, проверить HTTPS, загрузку реального установщика и отсутствие закрытых данных в ответах.
45. Провести полный smoke-test с сайта на чистой машине. Опубликовать changelog, известные ограничения и способ отправить bug report.

Выход: alpha, которую другой человек может установить по инструкции. Дальше — обратная связь, исправления и следующий небольшой релиз.

## Как выполняется каждая задача

1. Открыть issue, прочитать зависимости и критерии. Не начинать блокируемую интеграцию без результата зависимости.
2. Зафиксировать минимальный проверяемый результат; сложную задачу разбить на несколько этапов внутри issue.
3. Реализовать с учётом существующих контрактов. Новое архитектурное решение записать в ADR.
4. Выполнить подходящие тесты. Для поведения в игре нужны ручные шаги и наблюдения, компиляции недостаточно.
5. Просмотреть diff, выполнить `git diff --check`, сделать содержательный commit со ссылкой `Refs #N` и push.
6. Проверить GitHub Actions. Зелёный CI не заменяет ручные критерии.
7. Приложить свидетельства к issue и закрыть только после всех критериев. Незавершённые проверки остаются открытыми.

Статусы: open — запланировано/в работе; milestone задаёт этап. Прогресс отмечается checklist и коммитами. При блокировке записываем конкретную зависимость. Закрытый issue означает проверенный результат, а не просто наличие кода.

## Планирование времени и следующая очередь

Сначала оценивать задачи на небольшие проверяемые срезы; даты релиза назначить после проверки мира и Microsoft API. Не обещать фиксированный срок без этих двух результатов. Параллельно можно вести сайт и игровой код, но это не сокращает критическую цепочку авторизации/запуска.

Ближайшая очередь: SC-16 → SC-17 → SC-18, затем веб-задачи по зависимостям; SC-20 можно выполнять после ТЗ. Игровые задачи продолжатся после текущего веб-среза. Канонический живой статус: [GitHub Issues](https://github.com/AdilSatuv/spaceclient/issues); ссылки на все задачи — TASKS.md. JSON содержит исходное разбиение и критерии, но не подменяет статусы GitHub.
